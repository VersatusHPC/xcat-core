fix(ddns): a FIPS named rejects the hmac-md5 TSIG key, and one cluster gets two algorithms

makedns fails on a management node in FIPS mode when the site table names no OMAPI algorithm. named reports no error for the key stanza it loaded and then refuses every dynamic update signed with that key: it logs `tsig verify failure (BADSIG)`, answers SERVFAIL, and makedns reports FORMERR.

`site.dhcpomapialgorithm` is the cluster-wide choice, and every management node and service node reads it. xcatconfig wrote it for a new installation on EL9 or later and Ubuntu 20.04 or later, and left a new EL8 installation on the hmac-md5 default. `update_namedconf` in `xCAT-server/lib/xcat/plugins/ddns.pm` left a key stanza with no algorithm clause in place, and named refuses to load one.

`new_install_default_algorithm` now pins hmac-sha256 from EL8. On AlmaLinux 8.10 (dhcp-server-4.3.6-50.el8_10) `omshell` creates a host object over an hmac-sha256 OMAPI key with `key-algorithm hmac-sha256` and the right secret, is rejected by the server with a wrong secret, and cannot connect at all with the command left out or given a bogus name. `update_namedconf` repairs a stanza that names no algorithm. The documents name the one `chdef` a FIPS cluster needs when the attribute was never written for it. Ubuntu 18.04, SLES 12, SLES 15 and openSUSE Leap 15 keep hmac-md5: their `omshell` has no `key-algorithm` command, and no host of those was reachable to probe.

`xCAT-test/unit/ddns_tsig_default_algorithm.t` runs the makedns half on one host and the makedhcp half on another over one deployed state, and compares the two rendered key stanzas. It covers `makedns -e` with `site.externaldns` unset, an EL10 management node with a SLES 15 and with a Debian 12 service node, a missing key file, a key file the host cannot read, a key stanza with no algorithm clause, and a cluster with no stanza; it also asserts every platform resolves one algorithm when the site table names none, and that a new installation is never pinned to an algorithm its `omshell` may reject. Three of its six subtests fail without the fix commit.

An earlier revision of this branch changed the unset default from hmac-md5 to hmac-sha256 for every cluster, and computed it per host from the local platform, the local `-e` flag and the local `/etc/xcat/ddns.key`. That split a cluster whose hosts differ, and no xCAT command repaired the split. The default is unchanged again: the algorithm comes from the site table alone.

*unchecked*: the `omshell` of Ubuntu 18.04, SLES 12, SLES 15 and openSUSE Leap 15. No host of those exists in the lab (`xcat-master-suse` is not defined on either libvirt host), so those platforms keep the hmac-md5 they have today. The EL8 probe (a dhcpd with an hmac-sha256 OMAPI key inside a network namespace, driven by `omshell` with and without `key-algorithm`) settles each of them in one run.

Reproduced on xcat52-mn, AlmaLinux 9.8 with FIPS mode enabled, xCAT-2.19.0-snap202609021541. With `site.dhcpomapialgorithm` unset and an hmac-md5 key stanza, makedns returns 1 and named logs `tsig verify failure (BADSIG)`; one update signed the way the plugin signs it answers SERVFAIL and the record does not resolve. With `site.dhcpomapialgorithm=hmac-sha256`, makedns returns 0, named logs the zone update, the stanza reads hmac-sha256 with the same secret, and the record resolves.
